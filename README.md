# 多中心患者编号对照系统

多中心研究场景下的数据工程工具：归并各医院院内患者编号，维护"同人关系"并自动
形成研究取数用的编号对照表。基于 **Flask + SQLite（WAL）**，后台异步分组计算，
提供可演示的 Web 入口与 Docker Compose 一键启动环境。

## 一、快速启动

### 方式 1：Docker Compose（推荐交付方式）

```bash
docker compose up --build -d
# 浏览器打开 http://localhost:8000
docker compose logs -f          # 查看日志
docker compose down             # 停止；数据保留在命名卷 patient_data 中
```

### 方式 2：本地 Python 运行

```bash
pip install -r app/requirements.txt
./run_local.sh                  # 或：gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 8 app:app
# 浏览器打开 http://localhost:8000
```

数据默认写入 `./data/`（`patients.db` + `uploads/`），可用环境变量
`APP_DATA_DIR` / `APP_DB_PATH` / `APP_UPLOAD_DIR` 覆盖。

## 二、演示路径（约 3 分钟）

1. 首页上传 `demo/batch_a.csv`，再上传 `demo/batch_b.csv`
   （后者含重传键 `H01/MRN-1001`，页面可见"复用"计数，记录号不重复分配）。
2. 进入 **核对关系** 页，用记录号确认同人，例如 `1 ↔ 3`、`3 ↔ 5`
   （传递成组，组号取组内最小记录号）。
3. 尝试冲突确认：对同组已含某医院编号的组，再确认该医院的另一编号会被拒绝，
   页面显示具体拒绝原因。
4. 撤销一条关系：若剩余关系仍有路径相连则不拆组，否则按剩余关系重新拆组。
5. **分组与下载** 页查看每个组的成员，下载 `patient_mapping.csv`
   （响应头 `X-Compute-Id` 标注本次下载对应的完整状态版本）。
6. 进入 **名单核验** 页，上传 `demo/partner_list.csv`（含研究编号、医院、院内编号）。
   报告会按提交时的分组版本逐行核对：`P01` 的研究编号落在两个不同组（研究编号多组），
   `H02/MRN-2001` 与 `H03/MRN-3001` 同组却是两个研究编号（同组多编号），
   `H99/MRN-9999` 未收录（未匹配），空行被标格式错误。页面列出涉及行与组，
   可下载整份报告。
7. 回 **核对关系** 页撤销一条关系使分组更新；再回名单核验页，旧报告标记
   **已过期**，但仍可按原版本查看与下载，内容不混入新数据。
8. 首页可查看任务进度条、失败任务与拒绝原因。

CSV 格式：患者导入表头需包含医院列（`hospital`/`医院`）与院内编号列
（`mrn`/`院内编号`），支持 UTF-8（含 BOM）。核验名单表头需包含研究编号列
（`study_id`/`研究编号`）、医院列与院内编号列，最多 1000 行。
示例见 `app/static/sample_patients.csv`、`app/static/sample_verification.csv`。

## 三、需求与实现对照

| 需求 | 实现方式 |
| --- | --- |
| 上传患者 CSV（医院、院内编号），组合唯一，递增记录号，同键重传复用 | `patients` 表 `UNIQUE(hospital, hospital_mrn)` + 自增主键；导入任务逐行 upsert，统计新增/复用 |
| 核对员确认、撤销两条记录的同人关系 | `/relations/confirm`、`/relations/revoke`；关系以无向边规范化（小 id 在前），ACTIVE 部分唯一索引防重 |
| 关系传递成组，组号取最小记录号 | 并查集求连通分量（`app/groups.py`），组号 = 分量内最小记录号 |
| 同组不得有同医院不同编号 | 每次计算逐组检测同医院多编号，冲突则整次计算 FAILED、**正式分组保持上一版不变**，原因入任务可查 |
| 撤销按剩余关系拆组，仍有其他路径不拆 | 撤销仅把边置 REVOKED，重算基于剩余 ACTIVE 边重建分量 |
| 后台计算，期间仍可导入/核对/查询，计算不占库写事务 | 后台守护线程；计算阶段在只读快照取数后即释放连接，并查集纯内存运算；仅发布阶段用一个短写事务 |
| 并发确认按提交时完整关系判定；合并违规的两次确认只成功一次，无关确认保留 | 所有写事务 `BEGIN IMMEDIATE` 串行化，确认在同事务内基于完整 ACTIVE 关系构建分量并模拟合并校验 |
| 关系、组成员、组号一起生效；迟到计算不恢复旧分组 | 发布在单事务内整体替换 `groups`；任务带关系序列号 `seq_cutoff`，计算/发布前比对最新序列，过期即作废并补排最新任务 |
| 每次查询或下载来自一个完整状态 | 所有读操作在单个只读快照事务内完成；下载带 `compute_id` 版本标识 |
| 失败不改正式分组 | 冲突/过期只更新任务状态，不触碰 `groups` |
| 重启保留成功变动，未完成操作标失败 | WAL 持久化；worker 启动时（在后台线程启动前同步执行）把所有 PENDING/RUNNING 任务置 FAILED 并注明"服务重启" |
| 页面可查进度、成员、拒绝原因，下载对照 CSV | 四个页面 + 任务进度条 + 失败原因区 + `/download/mapping.csv` |
| 上传含研究编号、医院、院内编号的名单 CSV，最多 1000 行 | `/verification` 上传；`parse_verification_csv` 校验三列表头，超过 1000 行整次拒绝并提示拆分 |
| 按提交时已发布的完整分组核对每行；无已发布分组时拒绝核验 | 报告绑定 `group_versions.compute_id`；读取成员与计算均在只读快照/事务外完成，保存时同事务复核版本，版本已变则按新版本重算 |
| 医院+院内编号组合未收录 -> 未匹配 | 与版本快照的 `(hospital, hospital_mrn)` 索引精确比对，标 `UNMATCHED` |
| 同一研究编号对应多个组 / 同组对应多个研究编号 -> 指出涉及行和组 | 按研究编号与组分别聚合，标 `CONFLICT_STUDY` / `CONFLICT_GROUP`，逐行写入涉及 CSV 行号与组号及说明 |
| 核验期间仍可导入、核对、下载；计算不占写事务 | 核验只在短只读快照内取成员，计算纯内存完成；仅保存报告用一次短写事务 |
| 整份报告绑定提交时版本、一次性保存；失败不留半份 | 元数据与全部逐行结果在同一写事务内 `executemany` 插入；任一失败整体回滚，不生成可下载报告 |
| 重启后完整报告仍可查 | 报告与逐行结果持久化在 SQLite，按 `report_id` 查询与下载 |
| 分组更新后旧报告标过期，可按原版本下载，不混入新数据 | 版本快照不可变；页面按当前最新版本动态标记"已过期"，下载只读该报告绑定的快照版本，内容恒定 |
| 浏览器可提交、查看问题行、下载报告 | 名单核验页：上传表单、报告列表、问题行明细、`/download/verification/<id>.csv` |

## 四、架构说明

```
app/
├── config.py       # 路径与轮询配置（环境变量可覆盖）
├── db.py           # 连接/Schema、WAL、IMMEDIATE 写事务、只读快照、分组版本快照
├── groups.py       # 并查集、连通分量、同医院冲突检测（纯函数）
├── services.py     # 导入入队、CSV 解析、确认/撤销、名单核验与报告保存
├── worker.py       # 后台线程：导入逐行入库、重算、原子发布、重启恢复
├── repository.py   # 只读查询：统计/进度/成员/失败原因/对照与核验报告下载
├── web.py          # Flask 路由
├── templates/      # 四个页面（导入与进度 / 核对关系 / 分组与下载 / 名单核验）
└── static/         # 示例 CSV（患者导入、核验名单）
tests/              # 25 个测试：算法纯函数 + 端到端 + 并发 + 重启 + 名单核验
demo/               # 演示用 CSV（患者批次、合作方核验名单）
```

### 分组版本与核验报告

- 每次发布新分组时，在**同一写事务**内把新成员写入不可变的
  `group_versions` / `group_version_members` 快照；`groups` 表只表示当前版本。
- 核验报告保存 `compute_id`，其逐行结果只依赖该版本快照。新版本发布不修改
  快照，因此旧报告下载内容恒定；页面按"报告版本 < 当前最新版本"动态显示
  **已过期**。
- 报告元数据与全部逐行结果在单个写事务内一次性写入；元数据先插入、明细写
  失败时会整体回滚（测试用 SQLite 触发器注入失败验证），不会留下半份结果。

### 并发与一致性模型

- **WAL 模式**：读写不互斥；写事务由 SQLite 全局串行化，配合 `busy_timeout`
  与应用层重试。
- **确认/撤销事务**：`BEGIN IMMEDIATE` 立即取写锁，后到的并发确认在同一完整
  关系状态上重新校验，因此"各自合法、合并不合法"的两个确认只有先提交者成功。
- **分组生命周期**：
  1. 关系变动在同一写事务内入队 RECOMPUTE（携带当前最大关系序列号）；
  2. worker 在只读快照中取数（读完即释放），事务外完成并查集计算；
  3. 发布前比对序列号，过期则作废并补排；检测到冲突则 FAILED 且不改分组；
  4. 通过后在单写事务内整体替换 `groups`，关系/成员/组号原子生效。
- **任务合并**：已有 PENDING 重算时只更新序列号，避免高频确认造成任务风暴。

## 五、测试

```bash
python3 -m pytest tests/ -v
```

覆盖：递增编号与同键复用、传递成组与最小组号、撤销拆组/替代路径保留、
同医院冲突检测、并发确认只成功一次且无关确认保留、幂等重复确认、
迟到计算作废、计算失败不覆盖正式分组、重启恢复、HTTP 上传与快照下载；
名单核验另覆盖：无已发布分组拒绝、未匹配/格式错误识别、两类多组冲突及涉及
行与组、版本绑定与过期后按原版本下载、1000 行上限、明细写入失败整体回滚、
保存前版本并发更新时重算、重启后报告仍可查、并发核验期间导入与下载可用。

## 六、运维备注

- 容器以单 gunicorn worker + 多线程运行（后台线程与 Web 同进程协作）；
  数据存于命名卷 `patient_data`，`docker compose down` 不删数据，
  `docker compose down -v` 才会清除。
- 健康检查：`GET /healthz`。
- 上传大小上限 32MB（`web.py` 可调）。
